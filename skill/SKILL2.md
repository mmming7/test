# 累计指标创建助手

本 skill 指导用户在系统中配置各类累计指标。

## 核心原理

系统中的事件分析模型在计算去重累计值时存在限制：
- 趋势图的数值仅能做简单相加，无法对用户 ID 进行去重
- 扩展时间范围功能最多只能扩展到过去 90 天

**核心解决思路**：用「指标值标签」预计算累计值 → 转换为「虚拟事件属性」→ 在事件分析模型中使用虚拟属性的聚合（最大值/最小值/中位数等）来实现累计指标。

关键组件说明：
- **指标值标签（用户标签）**：预计算某个主体在某个时间范围内的聚合值（总和、去重计数等），支持自动更新和历史版本
- **虚拟事件属性**：在事件上动态计算的属性，可以将标签值映射为事件属性
- **分析主体「事件名称」**：因为事件名称是每个事件永远不变的值，适合作为累计计算的锚点

### 方案选择原则

面对一个累计指标需求时，按以下优先级选择方案：

1. **优先使用平台内置能力**：如果系统的留存模型、事件分析模型已经内置了所需的累计指标（如「回访事件发生次数合计」「累计总和」等），直接使用，无需额外配置。
2. **需要自定义计数逻辑时使用虚拟属性**：如果需要筛选特定用户群、定义特殊的计数规则、或突破 90 天限制时，使用「标签 + 虚拟属性」扩展。
3. **虚拟属性 + 按元素分组用于分时累计**：按小时累计去重等需要展开时间维度的场景，使用虚拟属性生成时间列表 + 按元素分组。
4. **SQL 自定义查询作为兜底**：当平台内置功能和虚拟属性都无法满足时（如跨项目分析、复杂窗口计算），再考虑 SQL 自定义查询或 API 方案。

## 场景一：按小时累计去重人数

**适用需求**：展示每日按小时的累计去重用户数，例如累计新增人数按小时趋势图。

此需求有三种可能的实现路径：
- **虚拟属性 + 按元素分组（推荐）**：在事件分析模型内完成，不需额外权限，可视化直接，配置一次即复用
- **SQL 自定义查询**：需开通自定义查询权限，部分版本不支持，无法直接在事件分析看板中使用
- **API + 外部计算**：需开发资源，非实时

**推荐方案适用场景**：需要在事件分析模型中直接展示趋势图、用看板分享给团队成员。

### 步骤

1. **创建虚拟事件属性**：生成按小时的时间列表。

   判断事件是否为今日：
   - 若为今日：取事件时间和当前时间之间的整点小时列表
   - 若为非今日：取事件时间到 23:00 的整点小时列表

   ```sql
   if(
     date_diff('day', date("#event_time"), date(current_timestamp)) = 0,
     reduce(
       sequence(1, hour(current_timestamp) - hour("#event_time") + 1),
       array[],
       (s, x) -> s || date_format(date_add('hour', x - 1, "#event_time"), '%H:00:00'),
       s -> s
     ),
     reduce(
       sequence(1, 24 - hour("#event_time")),
       array[],
       (s, x) -> s || date_format(date_add('hour', x - 1, "#event_time"), '%H:00:00'),
       s -> s
     )
   )
   ```

2. **在事件分析模型中构建指标**：
   - 分组选择该虚拟属性
   - **关键**：在列表分组时选择「按元素」分组（而非按列表整体）
   - 指标选择触发用户数（去重）

## 场景二：按天计算过去N日累计数值

**适用需求**：按天计算过去N日累计数值，尤其适用超过 90 天的长期累计指标（事件分析模型默认扩展时间范围最多 90 天）。

### 步骤

1. **新增分析主体「事件名称」**：在「项目管理 → 分析主体」处创建。

2. **创建指标值标签**：
   - 分析主体：事件名称
   - 时区：需要分析的时区
   - 分析时段：过去 N 日（或自某日至今等，根据需求选择）
   - 指标值配置：用户完成某事件的某属性的总和（或去重计数等）
   - 更新方式：自动更新
   - 备份方式：自动备份
   - 是否生成历史版本：是
   - 历史版本时间范围：需超过在模型中需要分析的时间范围

3. **创建虚拟事件属性**：
   - 将步骤 2 中创建的标签复制到虚拟属性编辑栏中
   - 属性类型：数值
   - 关联事件：自动识别
   - 匹配方式：动态匹配

4. **在事件分析模型中计算累计值**：
   - 时区：分析时区
   - 时间聚合粒度：按天
   - 分析时段：自定义
   - 指标：选择「某事件的步骤3中创建虚拟属性的最大值」（最小值、中位数等均可，因为一天内所有事件的该属性值相同）

## 场景三：开服累计 N 天数据汇总

**适用需求**：查看项目上线以来或开服等关键时间节点之后累计每天的数据，包括累计新增人数、累计付费人数/金额、累计登录等。

### 步骤

1. **创建虚拟事件属性「上线天数」**：
   ```sql
   date_diff('day', date('2024-03-01'), date("#event_time")) + 1
   ```
   将 `2024-03-01` 替换为实际开服/上线日期。

2. **新增分析主体「事件名称」**：同场景二步骤 1。

3. **配置基础指标相关标签**（使用「用户标签 → 指标值标签」）：

   | 指标 | 标签配置说明 |
   |------|---------|
   | 累计N天新增人数 | 用户完成注册事件的次数 |
   | 累计N天登录人数 | 用户完成登录事件的次数 |
   | 累计N天付费人数 | 用户完成付费事件的次数 |
   | 累计N天首次付费人数 | 用户完成付费事件的次数，增加筛选「是否首次充=真」 |
   | 累计N天付费金额 | 用户完成付费事件的付费金额总和 |
   | 累计N天在线时长 | 用户完成在线时长事件的时长总和 |

   每个标签均需：

   - 选择分析主体为“事件名称”
   - 分析时段选择「关键时间节点至今」
   - 打开自动更新和自动备份
   - 添加历史版本

5. **创建事件虚拟属性**：将每个标签转换为虚拟事件属性（同场景二步骤 3）。

6. **在事件分析模型中搭建报表**：用虚拟属性的聚合来展示各项累计指标的趋势。

## 场景四：当月累计日均值

**适用需求**：计算本月截至动态今日的某个指标累计总量的日均值，并展示按天趋势图。

### 步骤

1. **新增分析主体「事件名称」**（同场景二步骤 1）。

2. **创建指标值标签**：计算事件名称主体在当月的累计产出总量。
   - 打开自动备份和自动更新
   - 在标签详情页的「版本管理」中批量计算所需月份的历史版本

3. **创建 2 个虚拟事件属性**：

   **属性一：转标签** — 将步骤 2 的标签转换为事件属性（同场景二步骤 3）。

   **属性二：计算当月累计日期天数**：
   ```sql
   date_diff('day', date(date_trunc('month', "#event_time")), date("#event_time")) + 1
   ```
   这计算的是当月 1 日到事件发生日的天数。

4. **在事件分析模型中搭建指标**：
   - 日均值 = 步骤 3 属性一（累计总量）/ 步骤 3 属性二（累计天数）
   - 时间聚合粒度：按天

## 场景五：留存模型中的阶段累计人数

**适用需求**：在留存分析中计算阶段累计人数，如过去 7 天新增用户累计付费用户数、阶段累计付费次数等。

直接在留存分析模型中使用系统自带的指标：

1. 进入「留存分析」模型
2. 配置初始事件（如注册）和回访事件（如付费）
3. 配置同时展示指标，选择周期累计的计算方法
4. 如需筛选初始人群，添加筛选条件进行过滤
5. 结果即可展示按天的累计指标数据

## 场景六：累计付费指标（综合示例）

**适用需求**：新建用户累计付费总额/人数/渗透率/人均次数，以及新增付费用户的复购指标。

### 在事件分析模型中实现

#### 前提准备

1. **确认注册日期属性**：
   - 优先使用上报的用户属性（如 `register_time`）
   - 如未上报，通过「首末次标签」找出首次注册时间。分析时段需覆盖开服至今，打开标签的自动更新

2. **创建生命周期天数属性**（用于筛选复购行为）：
   ```sql
   date_diff('day', date(ta_u."register_time"), date("#event_time"))
   ```

#### 累计指标配置

| 指标 | 在事件分析模型中的配置 | 说明 |
|------|----------------------|------|
| 新增用户累计付费总额 | 付费事件的付费金额的总和 | 分组项选“注册时间”属性，按天汇总；时间粒度选合计 |
| 新增用户累计付费人数 | 付费事件的触发用户数 | 同上 |
| 新增用户累计付费率 | 付费事件触发用户数 / 注册事件触发用户数 | 同上 |
| 新增用户累计付费人均次数 | 付费事件的用户均次数 | 同上 |
| 新增付费用户数 | 付费事件的触发用户数，筛选：注册时间相对付费事件时间在当天 且 生命周期天数 = 0 | 同上 |
| 次日累计复购人数 | 付费事件的触发用户数，筛选：生命周期天数 = 1 | 同上 |
| 3 日累计复购人数 | 付费事件的触发用户数，筛选：生命周期天数 in (1,2,3) | 同上 |
| 7 日累计复购人数 | 付费事件的触发用户数，筛选：生命周期天数 in (1,2,3,4,5,6,7) | 同上 |
| 累计复购率 | 累计复购人数 / 新增付费用户数 | 同上 |

### 在留存分析模型中实现

- **初始事件**：代表新增的事件（如注册）
- **回访事件**：代表付费的事件（如充值成功）
- **同时展示**：
  - 新增用户累计付费总额：计算付费金额的周期累计总和
  - 新增用户累计付费人数：计算付费用户数的周期累计总和
  - 新增用户累计付费渗透率：开启指标编辑，A 指标为计算充值成功事件的次数周期累计总和，筛选条件为“是否首次充值为真”，B 指标为新增事件的触发用户数
  - 新增用户累计付费人均次数：计算付费事件次数的周期累计人均值

若配置“新增付费用户 次日/3日/7日累计复购人数“指标
- **初始事件**：代表付费的事件（如充值成功），添加筛选条件“注册时间”相对付费事件时间在当天
- **回访事件**：代表付费的事件（如充值成功）
- **同时展示**：计算付费事件用户数的周期累计总和

## 通用操作参考

### 创建指标值标签的关键参数

| 参数 | 说明 |
|------|------|
| 分析主体 | 通常选择「事件名称」 |
| 时区 | 与分析的时区保持一致 |
| 分析时段 | 根据需求选择（过去N日、自某日至今日等） |
| 更新方式 | 选择「自动更新」 |
| 备份方式 | 选择「自动备份」 |
| 历史版本 | 必须开启，时间范围需覆盖分析需求 |

### 虚拟属性创建要点

- 属性类型：数值
- 关联事件：自动识别
- 匹配方式：动态匹配
- 如果标签计算的是去重值，虚拟属性会将结果作为数值属性映射到每个事件上，在事件分析中取最大值即可得到累计值

### 常见 SQL 片段

```sql
-- 上线/开服天数
date_diff('day', date('YYYY-MM-DD'), date("#event_time")) + 1

-- 当月累计天数
date_diff('day', date(date_trunc('month', "#event_time")), date("#event_time")) + 1

-- 生命周期天数
date_diff('day', date(ta_u."register_time"), date("#event_time"))

-- 时区校正（标签时区为 UTC+0 时）
date_add('hour', 0 - cast("#zone_offset" as int), "#event_time")

-- 时区校正（标签时区为 UTC+8 时）
date_add('hour', 8 - cast("#zone_offset" as int), "#event_time")
```

### 常见问题排查

1. **指标值标签数据为空**：检查分析时段是否覆盖了需要的时间范围，历史版本是否已计算完成。
2. **虚拟属性值不正确**：确认标签已转为数值类型，关联事件和匹配方式设置正确。
3. **事件模型中累计值异常**：确认聚合函数使用的是最大值（因为同一天所有事件的虚拟属性值相同）。
4. **多时区数据不准确**：需要使用 `#zone_offset` 进行时区校正。
5. **历史数据缺失**：标签需要开启历史版本并批量计算历史数据。
